# Kingdom 1241 — instructions for Claude

Community website for Kingshot Kingdom 1241 (rules, events, guides, tools, later KvK sign-ups and an admin panel). Free hosting: Vercel + Supabase; translations by Anthropic Claude (Gemini optional). The product plan with all phases is in `docs/PLAN.md`; setup and keys are in `SETUP.md`; the code map is in `README.md`. Read those before starting a task.

## Working agreement

- Work on a feature branch (`feat/<phase-or-topic>`), commit in small steps with clear messages, open a PR against `main` when done. Never commit secrets: `.env.local` is ignored, only `.env.example` is tracked.
- Before pushing, all of these must pass: `npm run lint`, `npm run typecheck`, `npm run test`, `npm run build`. The same four run in GitHub Actions (`.github/workflows/ci.yml`) on every PR; `main` is protected by that check and Vercel deploys `main`. Workflow actions are pinned to a commit (version in the comment) and the Supabase CLI to a version; Dependabot (`.github/dependabot.yml`) proposes the bumps, don't float them by hand.
- Node 24 everywhere: `.nvmrc` drives CI (`node-version-file`) and `engines.node` in package.json tells Vercel which runtime to use. Newer local versions work; don't lower it.
- Unit tests live in `tests/`, mirroring `src/` (`src/lib/kvk/access.ts` → `tests/lib/kvk/access.test.ts`), never next to the source file. Import the code under test through the `@/` alias. Add tests for any new pure logic (helpers, mappers, seed validity). `tests/architecture/client-boundary.test.ts` walks the imports of every `"use client"` file and fails when a server-only module (the HTML sanitiser, the Supabase clients, `auth/server`, the loaders, the translation pipeline) or a Node built-in becomes reachable; add new server-only modules to its list.
- Keep the site light: it runs on free tiers. No new dependencies without a clear reason, no client-side libraries for things CSS or a few lines can do, small images (hero portraits and the prep page's item icons are 128px and rendered with `unoptimized` to save image transformations), everything cacheable stays in the static shell. A Client Component never imports `RichText` or `@/lib/html`: sanitise on the server (`prepareRichText`) and pass the HTML string to `SanitizedHtml` (the rules page does this, and sends only the visitor's language, not every translation).
- For UI changes, check the result in a browser on a phone-width viewport (390px) and desktop, in light and dark mode, in Arabic (`/ar/...`) for RTL, and at the largest text size (press A+ twice, 125%) in German, whose strings are the longest. Nothing may clip or overflow horizontally. Playwright with the bundled Chromium works for screenshots.
- **Every browser, or hidden, never the error page** (the owner's rule, Oct 2026, after read-aloud crashed tours on Android): anything beyond plain HTML (speech, wake lock, Web Audio, clipboard, newer `Intl` parts) is feature-detected and guarded. Where a browser can't do it, its control doesn't show; when it fails, the feature goes quiet and the page stays. Check such features in Chromium and WebKit (Playwright has both), and remember Android Chrome's quirks (voices labelled `en_US`).
- **Guided tours**: **every new feature or page gets a guided tour by default** (the owner's standing rule, Oct 2026): markers, steps next to the feature, `tour.*` strings in all five languages (plain English for admin pages), the tour added to the targets test; read-aloud comes with `useGuidedTour`, so nothing extra is needed for the voice, but write steps as whole sentences that make sense heard (emoji are dropped, name buttons with `{{ui:<key>}}`). Only placeholder content waits (below). A page can have a "?" that walks through its parts, the page dimmed around the part each step explains (`useGuidedTour` in `src/components/tour/GuidedTour.tsx`, pure parts in `src/lib/tour/tour.ts`). Nothing opens by itself, so a shared link always lands on the work: the "?" is highlighted and a quiet "New here?" line shows until this device has opened or hidden that tour (localStorage `kd1241_tours`, per tour id and `version`; raise the version when new steps are worth seeing again). Steps point at `data-tour="…"` markers (the admin `Field`, `AdminSection` and `DateTimeField` pass on a `tour` prop) and are defined next to their feature (`src/lib/rally-sync/tours.ts`, `src/lib/admin/tours.ts`, `src/lib/kvk/tours.ts`, `src/lib/tour/home.ts`); the first *drawn* element with a marker counts (the header nav and the phone's bottom nav share `site-nav`), and a step whose marker isn't drawn on the page (another role, another state of the page, a locked page that only shows its password card) is left out when the tour starts (with none left, one "nothing to walk through right now" card shows, so a "?" never does nothing), so one tour fits leaders, watchers and coordinators, or moderators and administrators. Texts players see are `tour.*` UI strings in all five languages. A step about a labelled element (a button, a heading) takes that label's key as its title (`uiStep(target, key, "sync.copyChat")`), and a body that names a button writes `{{ui:<key>}}` instead of its words (`fillUiLabels` in `resolveSteps`), so the guide always uses the page's own words in every language; a test checks the keys exist and every language keeps them. Public pages put a `PageGuide` in the `PageHeader`'s `guide` slot (the "?" is labelled from tablet width up), Home has it in the hero; pages and sections whose content is still placeholder (Events, Rules, Guides; Home's announcements and events) get no steps until their content is real. Every admin page has its own guide in plain English (`ADMIN_TOURS`), opened from "Page guide" in the admin bar (`AdminGuide`, which picks the page from the path with `adminPageFor`): written so a new moderator needs no other instructions (what goes in each field, which password or link goes to whom, good practice); a new admin page gets a guide too. When you change a page that has a tour, keep its markers or update its steps: `tests/lib/tour/targets.test.ts` fails on a step without a marker. The open tour follows its element every frame (a live page moves things) and rebuilds its card for each step, because browser page translation swaps text nodes and an in-place text update would go unseen. The card's speaker reads each step aloud with the browser's own speech (`speechSynthesis`; pure parts in `src/lib/tour/voice.ts`; no audio files, no service): off until the visitor taps it, then remembered on the device for every tour (localStorage `kd1241_tour_voice`), and shown only where the device has a voice for the tour's language (`<html lang>`, or `lang: "en"` for the admin tours). `pickVoice` prefers the device's default voice and passes over Apple's character voices (Eddy, Grandpa, …, listed before the real ones); steps are spoken sentence by sentence because some voices stop part-way through a long utterance. A tour must never break its page: speech runs on the tour's own language tag (Android labels voices `en_US`, which `Intl` refuses), every speech call is guarded so a failure leaves the tour silent, and `TourBoundary` closes the tour instead of showing the error page if anything inside it throws.
- Seed content is boilerplate that admins will edit; don't invent "real" kingdom facts (alliances, times, rules). Mark placeholders clearly.
- This is a noindex community site; keep it that way (`robots.ts` + robots meta in the root layout).

Never add an open-source license or copy code in from projects whose license would require opening it (GPL-style). Files with novel logic start with a one-line copyright notice (`// Copyright (c) 2026 Rajdeep Biswas. All rights reserved. …`): Rally Sync, the KvK prep days, the calculators, the live battle-time tokens, the rally-leader pets timing, the feedback AI step and Governor verification, and the translation pipeline, tests included. Give new files of those features (and of any new feature that is more than a form behind a password) the same line; standard parts (gates, admin forms, the checklist, backups) go without.

## Next.js 16 rules (Cache Components is ON)

`AGENTS.md` is right: this Next.js differs from older training data. Consult `node_modules/next/dist/docs` for anything Next-specific. Rules that matter here:

- Data loaders in `src/lib/data/index.ts` are `"use cache"` functions with `cacheLife("content")` (5-minute profile defined in `next.config.ts`) and `cacheTag(...)`. Add new content loaders the same way and register their table → tag in `cacheTagForTable` (`src/lib/data/cache-tags.ts`, pure; a test checks every translatable table has a tag and a webhook trigger). Invalidate with `revalidateTag(tag, { expire: 0 })` in route handlers (webhook, `/api/revalidate`).
- Never call `cookies()`, `headers()`, `searchParams` or `Date.now()`/`new Date()` in Server Components outside a cache or Suspense boundary; it breaks prerendering. Time-dependent UI (clock, countdowns, expiry checks) lives in Client Components using `useNow()` (`src/components/time/useNow.ts`), which returns `null` until hydrated.
- Any date that is part of the server-rendered HTML must be formatted with `timeZone: "UTC"` (Vercel renders in UTC, the visitor's browser in their zone; a different day → React hydration error #418 in production only). Visitor-local times are rendered only after `useNow()` returns a value.
- Client hooks that read the URL (`usePathname`, `useParams`, `useSelectedLayoutSegment`, `useSearchParams`) must sit in a small leaf component wrapped in `<Suspense>` — see `src/components/layout/NavLink.tsx`. Event handlers may read `window.location` directly.
- Routes with dynamic params below `[locale]` should `await params` inside a Suspense boundary (see `guides/[slug]/page.tsx`) and provide `generateStaticParams`.
- The root layout is `src/app/[locale]/layout.tsx`; `[locale]` is a root param, read it with `import { locale } from "next/root-params"`. `proxy.ts` (not middleware) adds the locale prefix to bare URLs and swaps a hidden language's prefix for the visitor's (`pathInLocale`); its copy of the enabled list is a minute old at most and is read again when a known language is missing (just shown), while the root layout checks the fresh list.
- React lint rules are strict: no `setState` directly inside effects (use `useSyncExternalStore` for external state), no impure calls during render.
- Tailwind v4: tokens are CSS variables in `src/app/globals.css` mapped through `@theme inline`; custom component classes live in `@layer components` and must not be `@apply`-ed by other classes (define a `@utility` instead, e.g. `tabular`, `no-scrollbar`). Dark mode is the `.dark` class, managed by the tiny store in `src/lib/theme.ts` (`useTheme` hook, `applyTheme`); no theme library. Buttons (`btn-*`) carry a 4px bottom shadow, so a row of buttons that can wrap uses `gap-x-2 gap-y-3` (a smaller row gap leaves the rows touching on a phone); `SectionTitle` wraps its actions onto their own line under a long title.
- Tailwind classes are linted by `eslint-plugin-better-tailwindcss` (part of `npm run lint`, which fails on warnings): canonical forms (`max-h-[28rem]` → `max-h-112`, `leading-tight` folded into `text-xs/tight`, `start-1` → `inset-s-1`, `[var(--x)]` → `(--x)`), shorthands, class order, duplicate/conflicting/unknown classes. Run `npx eslint --fix` to apply the automatic ones. `@apply` lines in CSS aren't linted — keep them canonical by hand. The `enforce-logical-properties` rule is off on purpose (it also rewrites heights and borders); keep using `ms-/me-/ps-/pe-/start-/end-/text-start` for the inline axis yourself.
- Visitor preferences (theme via the `dark` class, text size via `html[data-text-scale]`) live in localStorage and are re-applied by `src/components/layout/PersistentUiState.tsx` after a language switch remounts the root layout (React re-acquires `<html>` and wipes its class and attributes). Put any new per-device preference there, not in a component's own state. The theme and text-size init script is inserted into the server HTML through `useServerInsertedHTML` (`UiInit`), never rendered by React on the client: a language switch remounts the root layout and React warns about any `<script>` it has to recreate (that is also why next-themes was dropped). Text size scales the root font (87.5-125%), so size things in rem-based utilities (never `text-[11px]`, use `text-[0.6875rem]`), let text wrap (`break-words`, `line-clamp-*`) rather than `truncate`, give grid tracks and flex children `min-w-0`, and write single-column grids as `grid-cols-1` explicitly.
- Transitions: route changes crossfade through the `<ViewTransition>` in `src/app/[locale]/template.tsx` (a template remounts per navigation, so the old page exits and the new one enters). Never put that boundary in the layout: it would count as an in-place update and the browser would slide scrolled content to its new position. Theme and text-size changes wrap their DOM update in `withViewTransition()`, the language switch uses `withNavigationTransition()` (`src/lib/view-transition.ts`). The header and bottom nav carry a `view-transition-name` in globals.css so page content fades underneath them; `prefers-reduced-motion` turns every fade off; `html` must not have `scroll-behavior: smooth` (Next.js 16 no longer suppresses it during navigation, so the scroll-to-top would animate).

## Logging

- Server code logs through `createLogger(scope)` from `src/lib/log.ts` — never bare `console.*` in app code (CLI scripts in `scripts/` may print). Development output is pretty, production output is one JSON line per event (Vercel parses it). Levels: `debug` (per-batch detail), `info` (normal events), `warn` (degraded, e.g. seed fallback), `error` (needs a look).
- Route handlers and Server Actions take a request id with `requestId(request | headers)` (Vercel's `x-vercel-id`, else random), log with `log.child({ reqId })` and echo it as the `x-request-id` header. `proxy.ts` forwards it to pages.
- Never log secrets, passwords, cookies or full row contents; log ids, table names, counts and durations (`elapsedMs`).

## Internationalisation rules

- Every piece of text players see is translatable. Interface strings live in `src/content/seed/ui-strings.ts` (typed keys; English + hand-written de/ko/pl/ar); pages get them via `getDictionary(locale)` and pass the `Dictionary` object down as a prop to Client Components. Add a new key there with all five languages when you add UI text. Production reads them from the `ui_strings` table: a new key falls back to the bundled text automatically, but a **changed** key only reaches the site after `npm run db:seed -- --sync-ui` (or the Maintenance workflow's `sync-ui` task; run it once the Vercel deployment of that commit is live, because the translation webhooks are answered by whichever deployment is live). The machine-translated languages are reviewed with the `/translation-review` skill (`.claude/skills/translation-review/SKILL.md`, on the owner's Claude subscription): `npm run ui:review` exports the live strings read-only with the public key and runs the checks in `src/lib/i18n/ui-review.ts` (labels the page shows, glossary terms, placeholders, Japanese politeness, what changed since `state.json`), and fixes go into `src/content/seed/ui-reviewed.ts`: each entry repeats the English it was reviewed against, `withReviewed` lays it over the text in the seed (so `sync-ui` writes it, and the pipeline keeps it because the source hash is the English one) and in the bundled fallback, and a test fails once that English changes. The same skill reviews admin-written content (the active battle plan with its leader, checklist and feedback pages, and the public content): `npm run content:review` reads it with the service key (explicit columns only, never a password) and marks the languages a moderator corrected by hand (audit `translation.update`), checks in `src/lib/i18n/content-review.ts`; the fixes go into a JSON file outside the repository (battle-plan texts are secret, the repository is public; the review state is hashes in a git-ignored `*.local.json`) and the owner applies them with `npm run content:fixes -- --file … --apply`, which writes one language only while the English and that translation are still the reviewed ones (compare-and-swap, so a moderator's newer correction or a fresh machine translation is never overwritten), leaves `source_hash` alone and writes an audit entry `translation.review`. View first: a correct text is left alone even if it could be phrased better. Claude never writes these fixes to the database itself.
- Content fields are `Localized` JSON (`{ en, de, ... }`); read with `pick(value, locale)` which falls back to English. English is always the source language.
- Use logical CSS (`ms-`, `me-`, `ps-`, `pe-`, `start-`, `end-`, `text-start`) and `rtl:` variants, never left/right, so Arabic mirrors correctly. Put `dir="auto"` on elements that show content text (so English fallback reads correctly on RTL pages) and `dir="ltr"` on codes, numbers and clocks.
- Language list = `languages` table (seeded in `src/content/seed/languages.ts`); direction/font per code = `src/lib/i18n/languages.ts`. Adding a language means both places plus its glossary words and a translate run while it is still hidden (SETUP.md § 8.2a); the owner then shows it on the settings page. Latin, Korean and Arabic fonts are bundled; Japanese and Chinese use the device's fonts (`--font-japanese` / `--font-chinese` in globals.css) to keep the site light. UI strings for languages beyond the five hand-written ones come from the pipeline and are preserved by `--sync-ui` while the English text is unchanged.
- Translation is done only by the pipeline in `src/lib/translate`, triggered by Supabase webhooks → `POST /api/translate` or `npm run translate`. Never translate during a page render. Providers are behind `provider.ts` (`TRANSLATION_PROVIDER=anthropic|gemini|off`, auto-detected from the keys): `anthropic.ts` (Claude, default `claude-haiku-5-5`, structured JSON output, `fallbacks: "default"` only on models that have one: `fallbackOptions`, Haiku has none) and `gemini.ts` share the prompt, glossary (with a word for every site language, chosen to match what most of the UI already says), per-language style rules (`style` in `languages.ts`, e.g. Japanese です/ます), retry and JSON parsing; a new provider implements the same `translateFields` contract. Keep `off` working: the site must run with no provider at all. **Every Anthropic job defaults to Claude Haiku 5.5** (the owner's choice, Oct 2026: Opus ran up the API bill); `ANTHROPIC_MODEL`, `RETRO_TRANSLATE_MODEL` and `RETRO_ANALYSIS_MODEL` move a job to a larger model. Don't change a default without the owner; a test pins them. Rows carry a `source_hash` holding one hash per translatable column (JSON; older rows a single whole-row hash, honoured while it matches), so only the column whose English changed is sent to the model; keep that mechanism when adding tables (add them to `src/lib/translate/tables.ts` and `supabase/webhooks.sql`). Before writing a row back, the pipeline re-reads it and steps aside if the English changed meanwhile (a newer run owns it), merging only the languages it produced into the current value, so an admin's edit is never reverted by a slower run.

## Data and security

- Schema changes go in a new file `supabase/migrations/000N_<name>.sql` (don't edit `0001_init.sql` after it has been applied). Keep RLS on; the anon key may only read published rows. Writes use the service-role client (`src/lib/supabase/admin.ts`) from server code and scripts only — never import it in Client Components.
- Rich text is stored as HTML and must pass through `sanitizeRichText` on write and on render (`RichText` in Server Components; `prepareRichText` + `SanitizedHtml` when a Client Component has to render it).
- API routes that mutate or revalidate are protected by `TRANSLATE_WEBHOOK_SECRET` (`src/lib/api-auth.ts`). The public site stays login-free.
- **Admin area** (`src/app/[locale]/admin`, English only: it is the council's tool and the one exception to the i18n rule). Supabase Auth with Discord through `@supabase/ssr`. `src/lib/auth/server.ts` reads the session (`getCurrentUser`, cached per request; `checkAccess(role)` for actions) and must run behind Suspense or in an action/route; `proxy.ts` refreshes tokens for `/{locale}/admin` paths only and forwards `x-pathname`. **Next renders a page in parallel with its layouts, so a layout cannot keep page data out of the response**: `proxy.ts` sends signed-out visitors to the login page before anything renders, every admin page calls `requireEditor(locale)` before touching data, and the admin loaders return nothing without access (`checkAccess`); the `(gated)` layout only provides the chrome and the "no access" note. The login page sits outside the route group; `/auth/callback` finishes the OAuth flow. Session cookies are HttpOnly + Secure (`SESSION_COOKIE_OPTIONS`, passed to every `createServerClient`); the header/footer entry (`AdminEntry`) is a client component that reads a separate harmless marker cookie (`kd1241_admin`, set by the proxy/callback, cleared on sign-out; `src/lib/auth/session-hint.ts`, a hint only, never an access check) and shows the key when signed out, the wrench "Admin panel" when signed in, and nothing on `/admin` paths. Identity (`identityFromUser`) must come from `identities[].identity_data` and the identity's provider id, never from `user_metadata`, which any signed-in user can rewrite through the Auth API; `SITE_OWNER` is the Discord user id (production builds require it; a handle or an e-mail still works locally). Roles live in `profiles.role` (`admin` > `moderator` > `member`, helpers in `src/lib/auth/roles.ts`); the owner is configured, not stored (`SITE_OWNER`: the Discord user id; a handle or an e-mail in development, optionally a comma-separated list locally; `src/lib/auth/owner.ts`): always admin, unchangeable, and alone appoints or removes admins (`roleChangeProblem`, `removeAccountProblem`), admins appoint moderators; `removeAccount` deletes the Auth user (profile cascades). Pre-authorisations live in `role_grants` (matched on sign-in by Discord handle or e-mail, and re-applied at every sign-in, so `setRole` on a demotion and `removeAccount` revoke the matching ones through `grantsFor`); every write goes to `audit_log` (`systemAudit` for events without an actor). Admin reads are uncached service-role loaders (`src/lib/admin/*-data.ts`); writes are Server Actions (`src/lib/admin/*-actions.ts`) that parse `FormData` with the pure, unit-tested helpers in `forms.ts` / `kvk-forms.ts` (`uuidField`, `localeField`, …), re-check the role, reply through `action-helpers.ts` (`denied`, `invalid`, `failed`, the shared messages), log through `actionLogger()` (the admin logger with the request id), call `updateTag(CACHE_TAGS.kvk)` and `revalidatePath` of the editor. Actions that redirect instead of returning a state report problems through `?error=` on the target page (`EDITOR_NOTICES`, `NOTICES`). `moveRow` returns an `ActionState` so the arrows can show a failure; it writes the new order one row at a time. Write Localized columns through `localizedUpdate` (translations are kept only while the English is unchanged; the pipeline refills them). Child rows (`kvk_rules`, `kvk_coordinators`, `kvk_formations`) are never numbered by hand: inserts append (`nextSortOrder`) and the `MoveButtons` arrows call `moveRow`, which swaps neighbours and renumbers the list (pure `moveInList`). The language of the editor is a dropdown (`LanguagePicker`, `?lang=`), not pills, so it scales with the language list. Translated text is edited per language: English through the normal forms (`localizedUpdate` drops the other languages, the pipeline refills them), every other language through `saveTranslation` (`src/lib/admin/translation.ts`: writes one key with `withLanguage`, never touches `source_hash`, and refuses while `translationPending` so a running machine translation can't overwrite a manual fix). Profiles carry a self-declared `game_name` and `alliance_tag`, shown together as `[TAG] Name` (`formatGameName` in `src/lib/admin/profile.ts`, also the audit actor name; `parseProfileForm` splits a typed `[TAG]` prefix off the name); roles are still granted on the Discord handle. `ADMIN_DEV_LOGIN=1` plus `npm run dev:admin` give a password login in development builds only. **Owner settings** (`/admin/settings`, migration 0016): the owner's own pages, five tabs that are each a route of their own (General at `settings/`, then `settings/usage`, `settings/rally-sync`, `settings/alliances`, `settings/languages`): `SettingsTabPage` (`src/components/admin/SettingsFrame.tsx`) checks the owner before any data, draws the heading and tabs, and loads only that tab's part (`getGeneralSettings`, `getUsageSettings`, `getRallyCapacitySettings`, `getAllianceSettings`, `getLanguageSettings`); every save revalidates its own tab, and one page guide covers all tabs (steps for parts not on the open tab are left out). The "Settings" link and the pages show for `isOwner` only; actions re-check with `checkOwner()`; shows who the owner is (read-only: the owner and the kingdom are set up once, never in the site) and holds runtime settings in `app_config` (one JSON value per key, service role only, no RLS policy, backed up; `src/lib/config/app-config.ts` reads and writes, each feature parses its value tolerantly so a missing row or table means its defaults). Every save writes `config.update` to the audit log with the old and new values; the capacity save also expires `CACHE_TAGS.config`. It holds the Rally Sync capacity (below), the alliances (below), the wrong-password rules (`password_rules`: `src/lib/kvk/password-rules.ts`, defaults = `ADDRESS_POLICY` / `PLAN_ALERT`, read by the KvK and Rally Sync unlock actions through `getPasswordRules()`), the feedback defaults (`feedback_defaults`: `src/lib/retro/form-defaults.ts`, what a new form's `RetroSettingsForm` starts with) and the translation pause (`translation`: `src/lib/translate/pause.ts`; while paused `/api/translate` only revalidates, `npm run translate` refuses, the feedback AI actions refuse and the editors say so instead of "unlocks automatically"); number settings go through the pure `src/lib/config/numbers.ts`, and the site reads every setting through `src/lib/config/settings.ts` (uncached, never throws: defaults on any problem). The same page lists the languages (`languages` table, service role, every row): ▲ ▼ order and Show/Hide as a draft in the browser, written by one Save (`saveLanguages`: `parseLanguageForm` wants the same languages back and English shown, `hideProblem`; one `languages.update` audit entry and one expiry of the languages tag, because every page shows the menu), with how many texts each lacks (`addCoverage` over `TRANSLATABLE_TABLES`). **A language is added in code, never on the page** (registry, glossary words, style, a seed row with `enabled: false`, Maintenance `translate` with its `language` input, `/translation-review`, then Show; SETUP.md § 8.2a). **Alliances** (the `alliances` table, what Home shows; migration 0017, code in `src/lib/alliances/`) follow MightPulse: each row is linked by the game's alliance id (`mightpulse_aid`, unique; the first sync links seed and hand-added rows by their tag), so a new tag or name follows. `syncAlliances` (`sync.ts`, server only, never throws) reads the kingdom's `alliance_power` ranking (one call, up to 100 rows) and every listed alliance by its tag (one call each, fresher; it counts only when its id matches, since a tag can pass to another alliance), plans the writes with the pure `planAllianceSync` (`sync-plan.ts`; parsers in `mightpulse-data.ts`) and writes tag, name, power, leader and members with `stats_source = 'mightpulse'`; the result and the ranking go to app_config `alliance_sync` for the page. It runs daily at `DAILY_SYNC_UTC` (Maintenance task `alliances` → `POST /api/alliances/sync`, protected by `TRANSLATE_WEBHOOK_SECRET`, 503 when MightPulse is unreachable; the MightPulse key stays in Vercel; a test ties the cron to the constant) and from the owner's Sync now (one-minute cooldown). Keep files idempotent (`if not exists`, `drop … if exists`) so a manual run and the CLI run can coexist. **Migrations must be additive and work with the previous deploy's code**: the database workflow and the Vercel deploy of the same commit run in parallel, so for a short while new code meets the old schema and old code the new one. Add columns with defaults, never drop or rename a column in the PR that stops using it (do that in a later one), and keep the code tolerant of the column being missing where it matters (`syncProfile` already is).
- Seed data: `npm run db:seed` inserts missing rows only; `--overwrite` replaces seed rows (and drops their translations).
- Backups: `npm run backup` (`scripts/backup.ts`, pure helpers in `src/lib/backup/`) dumps every table in `BACKUP_TABLES` into one file encrypted with AES-256-GCM under `BACKUP_PASSPHRASE`; the Maintenance workflow runs it every Monday and keeps the artifact 90 days. The repository is public, so a plain dump must never be uploaded. A new table goes into `BACKUP_TABLES` (in foreign-key order) or `NOT_BACKED_UP`; a test checks every migrated table is in one of them. Restore writes by primary key and never deletes; admins and moderators of a backup come back as `role_grants`. The webhook triggers (`supabase/webhooks.sql`) and the auth config (`supabase/config.toml`) are declared in the repo and applied with the Maintenance tasks `webhooks` and `config-push`, not by hand in the dashboard.
- Old Vercel deployments: the **Prune deployments** workflow (`scripts/prune-deployments.ts`, pure rules in `src/lib/vercel/prune.ts`) runs after every finished Vercel deployment (its `Vercel` commit status), daily and by hand (dry run by default) with the `VERCEL_TOKEN` secret, and deletes every finished deployment except the live one (looked up through the production domain's alias, so a rollback is safe), the one before it (`KEEP_PRODUCTION`), the newest preview of each open pull request and anything still building; it deletes nothing when it can't tell which deployment is live. One build is about 150 MB and the Hobby plan stores 10 GB, so keep build output lean.
- Function region: `vercel.json` runs Vercel Functions in Frankfurt (`fra1`), the city of the Supabase project (eu-central-1); Hobby allows one region. Server requests make several database calls in a row (a Rally Sync Re-sync about eight), so the two must stay together: from the default `iad1` each call crossed the Atlantic and a Re-sync lost about two seconds of its buffer. Moving the database means moving `regions`; `x-vercel-id` shows the region second (`arn1::fra1::…`).
