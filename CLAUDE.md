# Kingdom 1241 — instructions for Claude

Community website for Kingshot Kingdom 1241 (rules, events, guides, tools, later KvK sign-ups and an admin panel). Free hosting: Vercel + Supabase; translations by Anthropic Claude (Gemini optional). The product plan with all phases is in `docs/PLAN.md`; setup and keys are in `SETUP.md`; the code map is in `README.md`. Read those before starting a task.

## Working agreement

- Work on a feature branch (`feat/<phase-or-topic>`), commit in small steps with clear messages, open a PR against `main` when done. Never commit secrets: `.env.local` is ignored, only `.env.example` is tracked.
- Before pushing, all of these must pass: `npm run lint`, `npm run typecheck`, `npm run test`, `npm run build`. The same four run in GitHub Actions (`.github/workflows/ci.yml`) on every PR; `main` is protected by that check and Vercel deploys `main`. Workflow actions are pinned to a commit (version in the comment) and the Supabase CLI to a version; Dependabot (`.github/dependabot.yml`) proposes the bumps, don't float them by hand.
- Node 24 everywhere: `.nvmrc` drives CI (`node-version-file`) and `engines.node` in package.json tells Vercel which runtime to use. Newer local versions work; don't lower it.
- Unit tests live in `tests/`, mirroring `src/` (`src/lib/kvk/access.ts` → `tests/lib/kvk/access.test.ts`), never next to the source file. Import the code under test through the `@/` alias. Add tests for any new pure logic (helpers, mappers, seed validity). `tests/architecture/client-boundary.test.ts` walks the imports of every `"use client"` file and fails when a server-only module (the HTML sanitiser, the Supabase clients, `auth/server`, the loaders, the translation pipeline) or a Node built-in becomes reachable; add new server-only modules to its list.
- Keep the site light: it runs on free tiers. No new dependencies without a clear reason, no client-side libraries for things CSS or a few lines can do, small images (hero portraits and the prep page's item icons are 128px and rendered with `unoptimized` to save image transformations), everything cacheable stays in the static shell. A Client Component never imports `RichText` or `@/lib/html`: sanitise on the server (`prepareRichText`) and pass the HTML string to `SanitizedHtml` (the rules page does this, and sends only the visitor's language, not every translation).
- For UI changes, check the result in a browser on a phone-width viewport (390px) and desktop, in light and dark mode, in Arabic (`/ar/...`) for RTL, and at the largest text size (press A+ twice, 125%) in German, whose strings are the longest. Nothing may clip or overflow horizontally. Playwright with the bundled Chromium works for screenshots.
- **Guided tours**: a page can have a "?" that walks through its parts, the page dimmed around the part each step explains (`useGuidedTour` in `src/components/tour/GuidedTour.tsx`, pure parts in `src/lib/tour/tour.ts`). Nothing opens by itself, so a shared link always lands on the work: the "?" is highlighted and a quiet "New here?" line shows until this device has opened or hidden that tour (localStorage `kd1241_tours`, per tour id and `version`; raise the version when new steps are worth seeing again). Steps point at `data-tour="…"` markers (the admin `Field`, `AdminSection` and `DateTimeField` pass on a `tour` prop) and are defined next to their feature (`src/lib/rally-sync/tours.ts`, `src/lib/admin/tours.ts`, `src/lib/kvk/tours.ts`, `src/lib/tour/home.ts`); the first *drawn* element with a marker counts (the header nav and the phone's bottom nav share `site-nav`), and a step whose marker isn't drawn on the page (another role, another state of the page, a locked page that only shows its password card) is left out when the tour starts (with none left, one "nothing to walk through right now" card shows, so a "?" never does nothing), so one tour fits leaders, watchers and coordinators, or moderators and administrators. Texts players see are `tour.*` UI strings in all five languages. A step about a labelled element (a button, a heading) takes that label's key as its title (`uiStep(target, key, "sync.copyChat")`), and a body that names a button writes `{{ui:<key>}}` instead of its words (`fillUiLabels` in `resolveSteps`), so the guide always uses the page's own words in every language; a test checks the keys exist and every language keeps them. Public pages put a `PageGuide` in the `PageHeader`'s `guide` slot (the "?" is labelled from tablet width up), Home has it in the hero; pages and sections whose content is still placeholder (Events, Rules, Guides; Home's announcements, events and gift codes) get no steps until their content is real. Every admin page has its own guide in plain English (`ADMIN_TOURS`), opened from "Page guide" in the admin bar (`AdminGuide`, which picks the page from the path with `adminPageFor`): written so a new moderator needs no other instructions (what goes in each field, which password or link goes to whom, good practice); a new admin page gets a guide too. When you change a page that has a tour, keep its markers or update its steps: `tests/lib/tour/targets.test.ts` fails on a step without a marker. The open tour follows its element every frame (a live page moves things) and rebuilds its card for each step, because browser page translation swaps text nodes and an in-place text update would go unseen.
- Seed content is boilerplate that admins will edit; don't invent "real" kingdom facts (alliances, times, rules). Mark placeholders clearly.
- This is a noindex community site; keep it that way (`robots.ts` + robots meta in the root layout).
- The repository is public, but the code is not open source (`LICENSE`: all rights reserved, no reuse, no AI re-creation or training; `package.json` says `UNLICENSED`). Never add an open-source license or copy code in from projects whose license would require opening it (GPL-style). Files with novel logic start with a one-line copyright notice (`// Copyright (c) 2026 Rajdeep Biswas. All rights reserved. …`): Rally Sync, the KvK prep days, the calculators, the live battle-time tokens, the rally-leader pets timing, the feedback AI step and Governor verification, and the translation pipeline, tests included. Give new files of those features (and of any new feature that is more than a form behind a password) the same line; standard parts (gates, admin forms, the checklist, backups) go without.

## Next.js 16 rules (Cache Components is ON)

`AGENTS.md` is right: this Next.js differs from older training data. Consult `node_modules/next/dist/docs` for anything Next-specific. Rules that matter here:

- Data loaders in `src/lib/data/index.ts` are `"use cache"` functions with `cacheLife("content")` (5-minute profile defined in `next.config.ts`) and `cacheTag(...)`. Add new content loaders the same way and register their table → tag in `cacheTagForTable` (`src/lib/data/cache-tags.ts`, pure; a test checks every translatable table has a tag and a webhook trigger). Invalidate with `revalidateTag(tag, { expire: 0 })` in route handlers (webhook, `/api/revalidate`).
- Never call `cookies()`, `headers()`, `searchParams` or `Date.now()`/`new Date()` in Server Components outside a cache or Suspense boundary; it breaks prerendering. Time-dependent UI (clock, countdowns, expiry checks) lives in Client Components using `useNow()` (`src/components/time/useNow.ts`), which returns `null` until hydrated.
- Any date that is part of the server-rendered HTML must be formatted with `timeZone: "UTC"` (Vercel renders in UTC, the visitor's browser in their zone; a different day → React hydration error #418 in production only). Visitor-local times are rendered only after `useNow()` returns a value.
- Client hooks that read the URL (`usePathname`, `useParams`, `useSelectedLayoutSegment`, `useSearchParams`) must sit in a small leaf component wrapped in `<Suspense>` — see `src/components/layout/NavLink.tsx`. Event handlers may read `window.location` directly.
- Routes with dynamic params below `[locale]` should `await params` inside a Suspense boundary (see `guides/[slug]/page.tsx`) and provide `generateStaticParams`.
- The root layout is `src/app/[locale]/layout.tsx`; `[locale]` is a root param, read it with `import { locale } from "next/root-params"`. `proxy.ts` (not middleware) adds the locale prefix to bare URLs.
- React lint rules are strict: no `setState` directly inside effects (use `useSyncExternalStore` for external state), no impure calls during render.
- Tailwind v4: tokens are CSS variables in `src/app/globals.css` mapped through `@theme inline`; custom component classes live in `@layer components` and must not be `@apply`-ed by other classes (define a `@utility` instead, e.g. `tabular`, `no-scrollbar`). Dark mode is the `.dark` class, managed by the tiny store in `src/lib/theme.ts` (`useTheme` hook, `applyTheme`); no theme library.
- Tailwind classes are linted by `eslint-plugin-better-tailwindcss` (part of `npm run lint`, which fails on warnings): canonical forms (`max-h-[28rem]` → `max-h-112`, `leading-tight` folded into `text-xs/tight`, `start-1` → `inset-s-1`, `[var(--x)]` → `(--x)`), shorthands, class order, duplicate/conflicting/unknown classes. Run `npx eslint --fix` to apply the automatic ones. `@apply` lines in CSS aren't linted — keep them canonical by hand. The `enforce-logical-properties` rule is off on purpose (it also rewrites heights and borders); keep using `ms-/me-/ps-/pe-/start-/end-/text-start` for the inline axis yourself.
- Visitor preferences (theme via the `dark` class, text size via `html[data-text-scale]`) live in localStorage and are re-applied by `src/components/layout/PersistentUiState.tsx` after a language switch remounts the root layout (React re-acquires `<html>` and wipes its class and attributes). Put any new per-device preference there, not in a component's own state. The theme and text-size init script is inserted into the server HTML through `useServerInsertedHTML` (`UiInit`), never rendered by React on the client: a language switch remounts the root layout and React warns about any `<script>` it has to recreate (that is also why next-themes was dropped). Text size scales the root font (87.5-125%), so size things in rem-based utilities (never `text-[11px]`, use `text-[0.6875rem]`), let text wrap (`break-words`, `line-clamp-*`) rather than `truncate`, give grid tracks and flex children `min-w-0`, and write single-column grids as `grid-cols-1` explicitly.
- Transitions: route changes crossfade through the `<ViewTransition>` in `src/app/[locale]/template.tsx` (a template remounts per navigation, so the old page exits and the new one enters). Never put that boundary in the layout: it would count as an in-place update and the browser would slide scrolled content to its new position. Theme and text-size changes wrap their DOM update in `withViewTransition()`, the language switch uses `withNavigationTransition()` (`src/lib/view-transition.ts`). The header and bottom nav carry a `view-transition-name` in globals.css so page content fades underneath them; `prefers-reduced-motion` turns every fade off; `html` must not have `scroll-behavior: smooth` (Next.js 16 no longer suppresses it during navigation, so the scroll-to-top would animate).

## Logging

- Server code logs through `createLogger(scope)` from `src/lib/log.ts` — never bare `console.*` in app code (CLI scripts in `scripts/` may print). Development output is pretty, production output is one JSON line per event (Vercel parses it). Levels: `debug` (per-batch detail), `info` (normal events), `warn` (degraded, e.g. seed fallback), `error` (needs a look).
- Route handlers and Server Actions take a request id with `requestId(request | headers)` (Vercel's `x-vercel-id`, else random), log with `log.child({ reqId })` and echo it as the `x-request-id` header. `proxy.ts` forwards it to pages.
- Never log secrets, passwords, cookies or full row contents; log ids, table names, counts and durations (`elapsedMs`).

## Internationalisation rules

- Every piece of text players see is translatable. Interface strings live in `src/content/seed/ui-strings.ts` (typed keys; English + hand-written de/ko/pl/ar); pages get them via `getDictionary(locale)` and pass the `Dictionary` object down as a prop to Client Components. Add a new key there with all five languages when you add UI text. Production reads them from the `ui_strings` table: a new key falls back to the bundled text automatically, but a **changed** key only reaches the site after `npm run db:seed -- --sync-ui` (or the Maintenance workflow's `sync-ui` task; run it once the Vercel deployment of that commit is live, because the translation webhooks are answered by whichever deployment is live). The machine-translated languages are reviewed with the `/translation-review` skill (`.claude/skills/translation-review/SKILL.md`, on the owner's Claude subscription): `npm run ui:review` exports the live strings read-only with the public key and runs the checks in `src/lib/i18n/ui-review.ts` (labels the page shows, glossary terms, placeholders, Japanese politeness, what changed since `state.json`), and fixes go into `src/content/seed/ui-reviewed.ts`: each entry repeats the English it was reviewed against, `withReviewed` lays it over the text in the seed (so `sync-ui` writes it, and the pipeline keeps it because the source hash is the English one) and in the bundled fallback, and a test fails once that English changes. The same skill reviews admin-written content (the active battle plan with its leader, checklist and feedback pages, and the public content): `npm run content:review` reads it with the service key (explicit columns only, never a password) and marks the languages a moderator corrected by hand (audit `translation.update`), checks in `src/lib/i18n/content-review.ts`; the fixes go into a JSON file outside the repository (battle-plan texts are secret, the repository is public; the review state is hashes in a git-ignored `*.local.json`) and the owner applies them with `npm run content:fixes -- --file … --apply`, which writes one language only while the English and that translation are still the reviewed ones (compare-and-swap, so a moderator's newer correction or a fresh machine translation is never overwritten), leaves `source_hash` alone and writes an audit entry `translation.review`. View first: a correct text is left alone even if it could be phrased better. Claude never writes these fixes to the database itself.
- Content fields are `Localized` JSON (`{ en, de, ... }`); read with `pick(value, locale)` which falls back to English. English is always the source language.
- Use logical CSS (`ms-`, `me-`, `ps-`, `pe-`, `start-`, `end-`, `text-start`) and `rtl:` variants, never left/right, so Arabic mirrors correctly. Put `dir="auto"` on elements that show content text (so English fallback reads correctly on RTL pages) and `dir="ltr"` on codes, numbers and clocks.
- Language list = `languages` table (seeded in `src/content/seed/languages.ts`); direction/font per code = `src/lib/i18n/languages.ts`. Adding a language means both places plus `npm run translate`. Latin, Korean and Arabic fonts are bundled; Japanese and Chinese use the device's fonts (`--font-japanese` / `--font-chinese` in globals.css) to keep the site light. UI strings for languages beyond the five hand-written ones come from the pipeline and are preserved by `--sync-ui` while the English text is unchanged.
- Translation is done only by the pipeline in `src/lib/translate`, triggered by Supabase webhooks → `POST /api/translate` or `npm run translate`. Never translate during a page render. Providers are behind `provider.ts` (`TRANSLATION_PROVIDER=anthropic|gemini|off`, auto-detected from the keys): `anthropic.ts` (Claude, default `claude-haiku-5-5`, structured JSON output, `fallbacks: "default"` only on models that have one: `fallbackOptions`, Haiku has none) and `gemini.ts` share the prompt, glossary (with a word for every site language, chosen to match what most of the UI already says), per-language style rules (`style` in `languages.ts`, e.g. Japanese です/ます), retry and JSON parsing; a new provider implements the same `translateFields` contract. Keep `off` working: the site must run with no provider at all. **Every Anthropic job defaults to Claude Haiku 5.5** (the owner's choice, Oct 2026: Opus ran up the API bill); `ANTHROPIC_MODEL`, `RETRO_TRANSLATE_MODEL` and `RETRO_ANALYSIS_MODEL` move a job to a larger model. Don't change a default without the owner; a test pins them. Rows carry a `source_hash` holding one hash per translatable column (JSON; older rows a single whole-row hash, honoured while it matches), so only the column whose English changed is sent to the model; keep that mechanism when adding tables (add them to `src/lib/translate/tables.ts` and `supabase/webhooks.sql`). Before writing a row back, the pipeline re-reads it and steps aside if the English changed meanwhile (a newer run owns it), merging only the languages it produced into the current value, so an admin's edit is never reverted by a slower run.

## Data and security

- Schema changes go in a new file `supabase/migrations/000N_<name>.sql` (don't edit `0001_init.sql` after it has been applied). Keep RLS on; the anon key may only read published rows. Writes use the service-role client (`src/lib/supabase/admin.ts`) from server code and scripts only — never import it in Client Components.
- Rich text is stored as HTML and must pass through `sanitizeRichText` on write and on render (`RichText` in Server Components; `prepareRichText` + `SanitizedHtml` when a Client Component has to render it).
- API routes that mutate or revalidate are protected by `TRANSLATE_WEBHOOK_SECRET` (`src/lib/api-auth.ts`). The public site stays login-free.
- **Admin area** (`src/app/[locale]/admin`, English only: it is the council's tool and the one exception to the i18n rule). Supabase Auth with Discord through `@supabase/ssr`. `src/lib/auth/server.ts` reads the session (`getCurrentUser`, cached per request; `checkAccess(role)` for actions) and must run behind Suspense or in an action/route; `proxy.ts` refreshes tokens for `/{locale}/admin` paths only and forwards `x-pathname`. **Next renders a page in parallel with its layouts, so a layout cannot keep page data out of the response**: `proxy.ts` sends signed-out visitors to the login page before anything renders, every admin page calls `requireEditor(locale)` before touching data, and the admin loaders return nothing without access (`checkAccess`); the `(gated)` layout only provides the chrome and the "no access" note. The login page sits outside the route group; `/auth/callback` finishes the OAuth flow. Session cookies are HttpOnly + Secure (`SESSION_COOKIE_OPTIONS`, passed to every `createServerClient`); the header/footer entry (`AdminEntry`) is a client component that reads a separate harmless marker cookie (`kd1241_admin`, set by the proxy/callback, cleared on sign-out; `src/lib/auth/session-hint.ts`, a hint only, never an access check) and shows the key when signed out, the wrench "Admin panel" when signed in, and nothing on `/admin` paths. Identity (`identityFromUser`) must come from `identities[].identity_data` and the identity's provider id, never from `user_metadata`, which any signed-in user can rewrite through the Auth API; `SITE_OWNER` may be the Discord user id (preferred) or the handle. Roles live in `profiles.role` (`admin` > `moderator` > `member`, helpers in `src/lib/auth/roles.ts`); the owner is configured, not stored (`SITE_OWNER`: Discord handle, or an e-mail in development, optionally a comma-separated list locally; `src/lib/auth/owner.ts`): always admin, unchangeable, and alone appoints or removes admins (`roleChangeProblem`, `removeAccountProblem`), admins appoint moderators; `removeAccount` deletes the Auth user (profile cascades). Pre-authorisations live in `role_grants` (matched on sign-in by Discord handle or e-mail, and re-applied at every sign-in, so `setRole` on a demotion and `removeAccount` revoke the matching ones through `grantsFor`); every write goes to `audit_log` (`systemAudit` for events without an actor). Admin reads are uncached service-role loaders (`src/lib/admin/*-data.ts`); writes are Server Actions (`src/lib/admin/*-actions.ts`) that parse `FormData` with the pure, unit-tested helpers in `forms.ts` / `kvk-forms.ts` (`uuidField`, `localeField`, …), re-check the role, reply through `action-helpers.ts` (`denied`, `invalid`, `failed`, the shared messages), log through `actionLogger()` (the admin logger with the request id), call `updateTag(CACHE_TAGS.kvk)` and `revalidatePath` of the editor. Actions that redirect instead of returning a state report problems through `?error=` on the target page (`EDITOR_NOTICES`, `NOTICES`). `moveRow` returns an `ActionState` so the arrows can show a failure; it writes the new order one row at a time. Write Localized columns through `localizedUpdate` (translations are kept only while the English is unchanged; the pipeline refills them). Child rows (`kvk_rules`, `kvk_coordinators`, `kvk_formations`) are never numbered by hand: inserts append (`nextSortOrder`) and the `MoveButtons` arrows call `moveRow`, which swaps neighbours and renumbers the list (pure `moveInList`). The language of the editor is a dropdown (`LanguagePicker`, `?lang=`), not pills, so it scales with the language list. Translated text is edited per language: English through the normal forms (`localizedUpdate` drops the other languages, the pipeline refills them), every other language through `saveTranslation` (`src/lib/admin/translation.ts`: writes one key with `withLanguage`, never touches `source_hash`, and refuses while `translationPending` so a running machine translation can't overwrite a manual fix). Profiles carry a self-declared `game_name` and `alliance_tag`, shown together as `[TAG] Name` (`formatGameName` in `src/lib/admin/profile.ts`, also the audit actor name; `parseProfileForm` splits a typed `[TAG]` prefix off the name); roles are still granted on the Discord handle. `ADMIN_DEV_LOGIN=1` plus `npm run dev:admin` give a password login in development builds only.
- **Shared passwords** (battle plan, leader and checklist pages, Rally Sync rooms) get a *Suggest* button: `CodeSuggestInput` (`src/components/ui/`) fills in `randomDigits()` from `src/lib/random-code.ts` (six digits, Web Crypto with rejection sampling, never `Math.random`) and selects it; the field stays an uncontrolled input read through `FormData`.
- **KvK battle plan** (`/kvk`): the `kvk_*` tables have no anon read policy — read them only through `createAdminClient()` in server code (`getActiveKvkPlan`). The visitor's cookie is an HMAC of plan id + password (`src/lib/kvk/access.ts`; the secret is mandatory in production); verify it in a Server Component inside `<Suspense>` (`KvkGate`), strip `password` before passing the plan to any component, and keep the unlock check in the Server Action (`src/lib/kvk/actions.ts`). Wrong passwords go through `src/lib/kvk/throttle.ts` (pure) + `throttle-store.ts` (table `kvk_unlock_throttle`): per-address lockouts answered with "try again in …" and a per-plan hourly count that only alerts (`systemAudit` + `notifyCouncil` in `src/lib/alerts.ts`), never locks; nothing may ever sleep or lock out players because of other players' guesses. On any data problem return `null` (page shows "no plan"), never the seed plan. `battle_end_at` is optional (migration 0009; only `battle_at` must lie ahead, the end just has to follow it, and a past end may be entered later): `BattleCountdown` shows start–end and the badge goes starts in → in progress → ended, and without an end it keeps saying "Battle day!"; the admin save writes the column only when it is set or the row already has it, so it works before the migration lands. One `kvk_plans` row is active at a time; `event_type` says whether it is the internal castle battle or the cross-kingdom KvK (they alternate every two weeks). The intro may contain `{{when}}`, `{{date}}`, `{{time}}` and `{{utc}}` tokens (`src/lib/kvk/battle-tokens.ts`, pure and unit-tested): `BattlePlan` renders such an intro through the client `LiveIntro`, which fills them from `battle_at` in UTC until hydrated and in the visitor's zone and language afterwards (`Intl.RelativeTimeFormat`, no dictionary keys), so an intro never says "tomorrow" by hand. The translation prompt keeps `{{…}}` placeholders. `[KvK]` and `[TMP]` are the kingdom's two battle alliances (castle rallies / counter-rallies), not game terms. Attackers *rally*, defenders *garrison*: formation roles stay `rally_lead` / `rally_join` in the database for both sides, and `roleLabelKey(side, role)` (`src/lib/kvk/formations.ts`) picks the word shown (`kvk.role.rally_*`, `kvk.role.garrison_*`, or `kvk.role.lead|join` for "either side"); the admin form switches the words with the side dropdown.
- **Rally-leader plan** (`/kvk/leaders`, tables `kvk_leader_briefs` + `kvk_leader_rules` + `kvk_rally_leaders`, migration 0010): the same battle as the active plan, behind its **own** password (`kvk_leader_briefs.password`; the forms refuse the plan's password on either side). Locked pages are areas (`KvkArea` in `src/lib/kvk/access.ts`: `plan`, `leaders`, `checklist`): each has its own cookie (`KVK_AREA_COOKIES`), token (`areaAccessToken`; `plan` keeps the original token so issued cookies stay valid), throttle scopes (`planScope`/`addressScope` with the area) and unlock/lock actions; a new area adds an entry in each. `getActiveLeaderPlan` returns `null` without a published brief and never reads the plan's password. Each rally has a battle team (`team`: [KvK]/[TMP], what the leader plays in on the day) separate from the home `alliance_tag`, a translated `position`, an optional UTC `start_at` (cleared by `duplicatePlan`) and `pets_offset_minutes` after `battle_at` (null = no pets): pets boost for `PET_BOOST_MINUTES` (2 h) and the boost must end inside the battle (`latestPetsOffset`, checked in `parseRallyLeaderForm`; `src/lib/kvk/leaders.ts`, pure). Battles usually run 12:00–17:00 UTC (`STANDARD_BATTLE` in `src/lib/kvk/battle-window.ts`): the plan form fills it with one button, every plan may differ, and without times the standard length is assumed; times render through the client `RallyStart` / `PetsTime` (UTC until hydrated). Leader rules are do/don't/info lines with an `audience` (all, rally, garrison). Rules and rallies are child rows of the plan (`saveLeaderRule`, `saveRallyLeader`, `moveRow`, copied by `duplicatePlan`), edited on `/admin/kvk/[id]/leaders` (tabs in `PlanEditorTabs`). The header's KvK entry is a dropdown (`children` in `nav-items.ts`, `NavMenu.tsx`, a disclosure of plain links); feedback belongs to the plan only.
- **Commander checklist** (`/kvk/checklist`, tables `kvk_checklist_briefs` + `kvk_checklist_items` + `kvk_checklist_rules`, migration 0011): the third locked area of the active plan, for the battle commander and coordinators, with its **own** password; no two pages of a battle may share a password (`passwordClash` in `kvk-forms.ts`, checked by `savePlan` and by `savePageBrief` for the leader and checklist briefs, one `PageBriefForm` for both). `getActiveChecklistPlan` returns `null` without a published brief. Items have a `phase` (`before` battle day, battle `day` before the start, `during`, `after`), a translated `text` and optional `note`; the visitor ticks them off in localStorage per plan id (`ChecklistBoard`, pure helpers in `src/lib/kvk/checklist.ts`), nothing is stored on the server. Lines (`kvk_checklist_rules`) are do/don't/info with a `section`: the commander's orders or the general guidelines. Items and lines are child rows of the plan (`saveChecklistItem`, `saveChecklistRule`, `moveRow`, copied by `duplicatePlan`), edited on `/admin/kvk/[id]/checklist` (third tab in `PlanEditorTabs`).
- **KvK prep days** (`/kvk/prep`, public, no tables): the prep week is fixed in `src/lib/kvk/prep.ts` (pure, unit-tested): rounds start on Sunday 1 Nov 2026 (`FIRST_PREP_ROUND`) and repeat every 28 days; Day 0 (Sunday) and Days 1–4 run 00:00–24:00 UTC, Day 5 until the invasion at Saturday 10:00 UTC, shields stay up 10:00–22:00 UTC around the 12:00–17:00 UTC castle battle (`KVK_SATURDAY`), and the next round counts down from 22:00. Prep proper starts on Monday: before a round and on the get-ready Sunday the countdown runs to Day 1, and every day tab has its own countdown (`dayCountdown`: to its start, then to its end). `PREP_ITEMS` is the council's ✅/🆗/⚠/🚫 table and the one source of every day's lists (`dayPlan`); `PREP_TIPS` are the ❗ lines per day; `INTEL_STACK_STEPS` is the intel stacking card (00:00 clear, 08:00 complete without claiming, 16:00 leave open plus Master Pan's extra missions) shown the day before each ✅ intel day (`intelStackFor`); texts are `prep.*` UI strings. `PREP_POINTS` holds the points per use (the council's sheet, checked against kingshotdata.com's Kingdom of Power page; speedups are shown as "30 per minute (1 h = 1,800)") and `pointsOn` the per-day exceptions (trained troops count per troop on Day 4 only, on Day 5 only their speedups score). Icons live in `public/items/` as 128px WebP files (sources at least 128px, fetched as single files from kingshotdata.com, kingshot.net, kingshotwiki.com and g2384/Kingshot-Data, never crawled) and are mapped in `src/components/kvk/prep-labels.ts` (`ITEM_IMAGES`, `DAY_IMAGES`, `TIP_IMAGES`, …), drawn by `ItemIcon` with an emoji fallback; a test checks every mapped file exists, so delete a file when nothing maps to it. `PrepBoard` (page) and `PrepCard` (Home) are client components that render the same static page for everyone and pick today with `useNow()`. Changing the content is a PR, by the owner's choice; byes (no KvK match) are rare, so there is no skip switch: a shifted round is a change of `FIRST_PREP_ROUND`.
- **Rally Sync** (`/tools/rally-sync`, `/tools/rally-sync/[code]`, admin `/admin/rally-sync`; tables `rally_sync_rooms` + `rally_sync_leaders` + `rally_sync_instances`, migrations 0012–0015; code in `src/lib/rally-sync/`): rooms where each rally leader gets a UTC start time = hit − rally timer − march (`timing.ts`, pure, unit-tested: earliest hit / Re-sync = now + timer + longest march + buffer, stages waiting → ready (60 s) → high alert (15 s) → GO → passed, sound cues). Rooms are **not** tied to a battle plan: moderators create them (`createRallyRoom` in `src/lib/admin/rally-sync-actions.ts`, audited); anyone opens one with its 6-character code (`room.ts`, alphabet without 0/O/1/I/L) + password (scrypt hash, ≥ 6 characters) or the invite link (`#k=` key = HMAC of room id + password hash, so a new password kills old links). **Every browser that opens a room is an instance** (`rally_sync_instances`, migration 0014): the room cookie `kd1241_rs_<code>` is `<instance id>.<HMAC of room + instance>` (`instanceCookieValue`, `access.ts`), valid while the row exists (`roomAccess` in `session.ts`), so a password change keeps everyone who is in, and the coordinator removes one browser (or "log everyone else out") by deleting rows (`removeInstance` / `removeOthers` ops); a removed browser needs the password to come back, so removing usually goes with a new password. One player may run several instances (Chrome and Safari), each with its own leader (`rally_sync_leaders.instance_id`). The coordinator's "In the room" list (`listInstances`, `InstancesPanel`) shows each instance by its own name (`renameMe`: the watcher's "Set a name", or a leader's "Name of this browser" in their edit card for a proxy), else its leaders' names, else "Watcher" + a random 4-character `tag` (`instanceLabel`); joining as a leader clears a watcher name (the browser then follows the leader's name) and leaving keeps the leader's name on the browser; limit 50 per room (trigger). The Invite panel checks the device's saved link and password against the room whenever it opens (`invite` op with `password` → `passwordCurrent`) and drops what is stale. Cookies from before 0014 (HMAC of room id + password hash) are still accepted and issued while the table is missing (`not_migrated`), and leaders are read with `*`, so a deploy may run ahead of its migration. The coordinator token (`#c=` in the coordinator link) and each leader's token live in the browser (`device.ts`, localStorage) and only as sha256 hashes in the tables; every Server Action (`actions.ts`) re-opens the room, checks the cookie and the token. Limits (3 open rooms, 10 leaders per room, 15 across open rooms, 50 instances per room) and the "changed"/"closed" Realtime broadcast are database triggers (instances ping on join, rename, coordinator flag and removal, never on the heartbeat); the actions check the limits first for the message. A room is open while `last_seen_at` (bumped by `GET /api/rally-sync/[code]`, at most once a minute) is under 30 minutes old and the room is under 24 hours (`isRoomOpen`; the same rule in SQL `rally_sync_is_open`); a closed room is deleted on access, by pg_cron every five minutes and by `npm run prune`. **Realtime carries no data**: the browser joins a random per-room public broadcast topic with a small hand-written Phoenix client (`realtime.ts`; supabase-js stays server-only) and treats every ping as a hint to refetch through the cookie-checked route, which also returns the server clock for the countdown's offset (`clock.ts`); pages poll every 30 s while the link is down. The countdown ticks on corrected whole seconds (`useCorrectedSecond`), sounds are booked on the Web Audio clock (`sound.ts`); the screen-awake lock, sound and a game-clock adjustment (`gameOffsetSeconds`, ±60 s) are per-device settings. **The game clock is the source of truth**: stored hit/start/enemy times are game-clock times, shown unchanged on every device; the adjustment only moves the device's "now" (`toGameTime`, used for its clock, countdowns and sounds), and the coordinator's offset goes with every `coordinate` call so Re-sync, the "already passed" check and the check on a garrison tap's moment count from their game "now". The room page is deliberately minimal (no page header; one status line, the `FocusBlock` with the visitor's own start that becomes the alert (the start time keeps its size in every stage, since players start on the in-game clock; the countdown under it is the guide and stays smaller), their own entry as a highlighted card (edited or removed there, also by a coordinator who leads a rally), the other leaders as quiet `LeaderRow`s (stage colours only for the coordinator), coordinator extras under "More options"): keep new things out of the leaders' line of sight. `RALLY_SYNC_STORE=memory` (ignored on Vercel) swaps in `memory-store.ts` for local review, with a demo room `TEST23` / `review123` / `#c=local-review-coordinator`. **Nothing about a running rally changes under the leaders' feet** (a rally runs while the hit time is set and still ahead on the acting device's game clock, `rallyRunning`): each leader has a `status` (`active` in the current rally, `next` from the next hit time, `inactive` sitting out; `LeaderStatus` in `room.ts`). Joining or coming back from sitting out during a rally gives `next`; sitting out applies at once (it moves nobody else's time); a leader's own new march time during a rally waits in `next_march_seconds` (`leaderEdit`); setting or clearing a hit time starts the next rally (`startNextRally` in `actions.ts`: `next` → `active`, waiting march times take over). The coordinator's edits apply at once; Re-sync plans with next-rally march times and skips leaders sitting out (`resyncMarches`), and while a rally runs it needs a second tap within 4 s (the first arms it and shows the new time), so a stray tap can't replace a running hit time. Time fields take ↑ / ↓ (±1 s, Shift ±10 s; pure `stepTime` keeps the typed format, `stepKeys` wires it). Rooms are in `NOT_BACKED_UP`. **Garrison mode** (`garrison.ts`, pure, unit-tested; `Garrison.tsx`; migration 0015 adds the `garrison` jsonb column and the mode) is a third room mode, fixed at creation (`canSwitchMode`), for 20–30 defenders whose refill marches must land between two enemy rally hits on our castle (early → the garrison is still full and the troops turn back; late → the next hit lands first). The coordinator keeps the enemy rally leaders with the march time to our castle recorded from earlier hits (an active tick box; a changed march keeps the previous one for "use again", since pets speed a leader up for two hours) and marks each incoming rally on that leader's card, which keeps its place (no re-sorting): *Rally started*, then the countdown chip (`LAUNCH_CHIPS`, 4:45…3:00) or *Other* + *Now* at the moment the game shows that value. The tap moment is taken on the coordinator's corrected game clock (`exactNow`), accepted by the server within ±10 s (`tapMoment`, else its own now) and rounded to the second (`launchFromTap`). Until the rally launches −1 s / +1 s / *Re-time* move it; after launch the card counts down "Lands in" to the hit and only *Correct landing time* (a measured "lands in", `rallyLands`), which also saves that leader's march for later waves. Enemy hit = launch + march; refill windows lie between distinct hits at least 2 s apart and aim at most 3 s after the first (`refillWindows`); nothing is planned after the last hit. Players type their own march time and send spacing on their device only (`device.ts`, never sent), and `playerPlan` works out every send = window − march, planning a later send with a speedup when the spacing makes it late (a speedup cuts the remaining march: late by k s → 25 % when the march shows 4k left, else 50 % at 2k; `speedupFor`), with a chime 30 s ahead and ticks to GO for each send and speedup (`refillCues`). The cards of the next burst are big (`focusSteps`: taps at most `TOGETHER_SECONDS` = 5 s apart, decided from the plan so no card changes size mid-burst), the others small. A wave clears itself 30 s after its last hit (`currentWave`); *Clear all* takes two taps; *Copy for game chat* copies each enemy's hit and our refill landing times, one per line (`chatSummary`). Rally rooms have the same button once a hit time is set: the hit, the rally timer and every leader's start, earliest first, with a leader who was too late when the hit was set marked so. The chat texts come from `chat.ts` (`garrisonChat`, `rallyChat`, `counterChat`; pure, tested), the button is `CopyForChat`. Garrison edits rewrite one JSON value, so they compare-and-swap on `updated_at` (`updateRoomIf`, up to five rounds) instead of overwriting a second coordinator's tap. The memory store adds a demo garrison room `DEFEND` (same password and coordinator token as `TEST23`). **Counter-rally mode** (`counter.ts`, pure, unit-tested; `Counter.tsx`) is the counter alliance's launch order, not a timing: they can't see the enemy's rally, only their own alliance's (with its countdown) in the game, so `counterOrder` sorts the leaders by march, slowest first (sitting out left out), and gives everyone after the first a cue = rally timer − (their march − my march), the countdown of an earlier counter rally at which to start, so all land in the same second; from the third on two cues (the first rally and the one before) so slips don't add up, and a cue ≤ 0 becomes "N s after". Each cue is also shown as seconds after that rally started (`gapSeconds`, "+5 s") for leaders who count, and the coordinator copies either style (`counterChat(..., "countdown" | "seconds")`, two buttons). The leader's own cue is big (`CounterFocus`), the whole order below (`CounterSheet` through the shared `LeaderList`); no hit time, countdown or sound (hit ops are refused outside rally rooms, `HIT_OPS`). Every room mode is fixed at creation (`canSwitchMode` = same mode only); the old counter inputs (enemy "lands in" + offset) are gone and `counter_offset_seconds` / `enemy_hit_at` stay as unused columns until a later migration drops them. The memory store also has a demo counter room `CNTR22`. The status line's "?" opens the room's guided tour (one per mode, `RALLY_SYNC_TOURS` in `tours.ts`); its "New here?" line and highlight stay away while a rally runs or a garrison wave is coming in (`quietTour`).
- **Battle feedback** (`/kvk/feedback`, tables `kvk_retrospectives` + `kvk_retro_responses`, code in `src/lib/retro/`): one retrospective per plan, at most one `open` (unique partial index), behind the same cookie as the plan (`retroAccess` accepts the retrospective's plan or the active plan). Questions are a fixed catalogue in `questions.ts` (translated through `retro.q.*` / `retro.t.*` UI strings); the per-battle `config` JSON only says which are shown and required (`parseConfig` is tolerant; a hidden question is never required). Ratings are 0–5, texts ≤ 500 characters (checked in the form, in `parseRetroForm` and by the database). The Governor ID is checked through MightPulse (`mightpulse.ts`, `MIGHTPULSE_API_KEY`) **fail-open**: `unavailable` means the player types name and alliance and no message is shown; only a clear `unknown` (or another kingdom) blocks. A successful lookup hands the form a signed token (`governor.ts`) so the submission needs no second call and cannot change the verified name. Identity (`governor_id`, `game_name`) is returned by `listResponses` to the owner only; the CSV never has it; never log texts, names or ids. Per-address budgets reuse the `kvk_unlock_throttle` table (`mp:` and `retro:` scopes). Deleting one answer: moderator; all answers: admin; every write and the export go to `audit_log`. Retention counts from `battle_at` (`retention.ts`); `npm run prune` / Maintenance `prune` (daily) deletes due answers, closes the form and writes `retro.prune`. The AI step (`analyse.ts`, `ai.ts`, pure parts in `analysis.ts`), never automatic: the Results page's "Translate answers" (any moderator; `translateRetrospective` → `translateResponses`) translates each response's texts to English once (`texts_en`, `translated_at`, batches of 25, parallel), and "Translate and analyse" (`analyseRetrospective`, **the owner only**: one request reads every answer, the biggest AI call on the site, so the button is the owner's and the action re-checks `isOwner`; everyone else reads the stored summary) also stores one summary on the retrospective (`analysis`, `analysis_at`, `analysis_count`); same provider switch as the pipeline, `RETRO_TRANSLATE_MODEL` and `RETRO_ANALYSIS_MODEL` for Anthropic (both Haiku by default); the model's JSON is validated by `parseAnalysis` before anything is written and every run is audited with its tokens.
- Schema changes: add `supabase/migrations/000N_<name>.sql`; the Deploy database workflow applies it on merge (and dry-runs it on the PR). Keep files idempotent (`if not exists`, `drop … if exists`) so a manual run and the CLI run can coexist. **Migrations must be additive and work with the previous deploy's code**: the database workflow and the Vercel deploy of the same commit run in parallel, so for a short while new code meets the old schema and old code the new one. Add columns with defaults, never drop or rename a column in the PR that stops using it (do that in a later one), and keep the code tolerant of the column being missing where it matters (`syncProfile` already is).
- Seed data: `npm run db:seed` inserts missing rows only; `--overwrite` replaces seed rows (and drops their translations).
- Backups: `npm run backup` (`scripts/backup.ts`, pure helpers in `src/lib/backup/`) dumps every table in `BACKUP_TABLES` into one file encrypted with AES-256-GCM under `BACKUP_PASSPHRASE`; the Maintenance workflow runs it every Monday and keeps the artifact 90 days. The repository is public, so a plain dump must never be uploaded. A new table goes into `BACKUP_TABLES` (in foreign-key order) or `NOT_BACKED_UP`; a test checks every migrated table is in one of them. Restore writes by primary key and never deletes; admins and moderators of a backup come back as `role_grants`. The webhook triggers (`supabase/webhooks.sql`) and the auth config (`supabase/config.toml`) are declared in the repo and applied with the Maintenance tasks `webhooks` and `config-push`, not by hand in the dashboard.
