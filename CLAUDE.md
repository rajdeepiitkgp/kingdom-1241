# Kingdom 1241 — instructions for Claude

Community website for Kingshot Kingdom 1241 (rules, events, guides, tools, later KvK sign-ups and an admin panel). Free hosting: Vercel + Supabase; translations by Anthropic Claude (Gemini optional). The product plan with all phases is in `docs/PLAN.md`; setup and keys are in `SETUP.md`; the code map is in `README.md`. Read those before starting a task.

## Working agreement

- Work on a feature branch (`feat/<phase-or-topic>`), commit in small steps with clear messages, open a PR against `main` when done. Never commit secrets: `.env.local` is ignored, only `.env.example` is tracked.
- Before pushing, all of these must pass: `npm run lint`, `npm run typecheck`, `npm run test`, `npm run build`. The same four run in GitHub Actions (`.github/workflows/ci.yml`) on every PR; `main` is protected by that check and Vercel deploys `main`.
- Node 24 everywhere: `.nvmrc` drives CI (`node-version-file`) and `engines.node` in package.json tells Vercel which runtime to use. Newer local versions work; don't lower it.
- Unit tests live in `tests/`, mirroring `src/` (`src/lib/kvk/access.ts` → `tests/lib/kvk/access.test.ts`), never next to the source file. Import the code under test through the `@/` alias. Add tests for any new pure logic (helpers, mappers, seed validity).
- Keep the site light: it runs on free tiers. No new dependencies without a clear reason, no client-side libraries for things CSS or a few lines can do, small images (hero portraits are 128px and rendered with `unoptimized` to save image transformations), everything cacheable stays in the static shell.
- For UI changes, check the result in a browser on a phone-width viewport (390px) and desktop, in light and dark mode, in Arabic (`/ar/...`) for RTL, and at the largest text size (press A+ twice, 125%) in German, whose strings are the longest. Nothing may clip or overflow horizontally. Playwright with the bundled Chromium works for screenshots.
- Seed content is boilerplate that admins will edit; don't invent "real" kingdom facts (alliances, times, rules). Mark placeholders clearly.
- This is a noindex community site; keep it that way (`robots.ts` + robots meta in the root layout).

## Next.js 16 rules (Cache Components is ON)

`AGENTS.md` is right: this Next.js differs from older training data. Consult `node_modules/next/dist/docs` for anything Next-specific. Rules that matter here:

- Data loaders in `src/lib/data/index.ts` are `"use cache"` functions with `cacheLife("content")` (5-minute profile defined in `next.config.ts`) and `cacheTag(...)`. Add new content loaders the same way and register their table → tag in `cacheTagForTable`. Invalidate with `revalidateTag(tag, { expire: 0 })` in route handlers (webhook, `/api/revalidate`).
- Never call `cookies()`, `headers()`, `searchParams` or `Date.now()`/`new Date()` in Server Components outside a cache or Suspense boundary; it breaks prerendering. Time-dependent UI (clock, countdowns, expiry checks) lives in Client Components using `useNow()` (`src/components/time/useNow.ts`), which returns `null` until hydrated.
- Any date that is part of the server-rendered HTML must be formatted with `timeZone: "UTC"` (Vercel renders in UTC, the visitor's browser in their zone; a different day → React hydration error #418 in production only). Visitor-local times are rendered only after `useNow()` returns a value.
- Client hooks that read the URL (`usePathname`, `useParams`, `useSelectedLayoutSegment`, `useSearchParams`) must sit in a small leaf component wrapped in `<Suspense>` — see `src/components/layout/NavLink.tsx`. Event handlers may read `window.location` directly.
- Routes with dynamic params below `[locale]` should `await params` inside a Suspense boundary (see `guides/[slug]/page.tsx`) and provide `generateStaticParams`.
- The root layout is `src/app/[locale]/layout.tsx`; `[locale]` is a root param, read it with `import { locale } from "next/root-params"`. `proxy.ts` (not middleware) adds the locale prefix to bare URLs.
- React lint rules are strict: no `setState` directly inside effects (use `useSyncExternalStore` for external state), no impure calls during render.
- Tailwind v4: tokens are CSS variables in `src/app/globals.css` mapped through `@theme inline`; custom component classes live in `@layer components` and must not be `@apply`-ed by other classes (define a `@utility` instead, e.g. `tabular`, `no-scrollbar`). Dark mode is the `.dark` class, managed by the tiny store in `src/lib/theme.ts` (`useTheme` hook, `applyTheme`); no theme library.
- Tailwind classes are linted by `eslint-plugin-better-tailwindcss` (part of `npm run lint`, which fails on warnings): canonical forms (`max-h-[28rem]` → `max-h-112`, `leading-tight` folded into `text-xs/tight`, `start-1` → `inset-s-1`, `[var(--x)]` → `(--x)`), shorthands, class order, duplicate/conflicting/unknown classes. Run `npx eslint --fix` to apply the automatic ones. `@apply` lines in CSS aren't linted — keep them canonical by hand. The `enforce-logical-properties` rule is off on purpose (it also rewrites heights and borders); keep using `ms-/me-/ps-/pe-/start-/end-/text-start` for the inline axis yourself.
- Visitor preferences (theme via the `dark` class, text size via `html[data-text-scale]`) live in localStorage and are re-applied by `src/components/layout/PersistentUiState.tsx` after a language switch remounts the root layout (React re-acquires `<html>` and wipes its class and attributes). Put any new per-device preference there, not in a component's own state. The theme and text-size init script is inserted into the server HTML through `useServerInsertedHTML` (`UiInit`), never rendered by React on the client: a language switch remounts the root layout and React warns about any `<script>` it has to recreate (that is also why next-themes was dropped). Text size scales the root font (87.5-125%), so size things in rem-based utilities (never `text-[11px]`, use `text-[0.6875rem]`), let text wrap (`break-words`, `line-clamp-*`) rather than `truncate`, give grid tracks and flex children `min-w-0`, and write single-column grids as `grid-cols-1` explicitly.
- Transitions: route changes crossfade through the `<ViewTransition>` in `src/app/[locale]/template.tsx` (a template remounts per navigation, so the old page exits and the new one enters). Never put that boundary in the layout: it would count as an in-place update and the browser would slide scrolled content to its new position. Theme and text-size changes wrap their DOM update in `withViewTransition()`, the language switch uses `withNavigationTransition()` (`src/lib/view-transition.ts`). The header and bottom nav carry a `view-transition-name` in globals.css so page content fades underneath them; `prefers-reduced-motion` turns every fade off; `html` must not have `scroll-behavior: smooth` (Next.js 16 no longer suppresses it during navigation, so the scroll-to-top would animate).

## Logging

- Server code logs through `createLogger(scope)` from `src/lib/log.ts` — never bare `console.*` in app code (CLI scripts in `scripts/` may print). Development output is pretty, production output is one JSON line per event (Vercel parses it). Levels: `debug` (per-batch detail), `info` (normal events), `warn` (degraded, e.g. seed fallback), `error` (needs a look).
- Route handlers and Server Actions take a request id with `requestId(request | headers)` (Vercel's `x-vercel-id`, else random), log with `log.child({ reqId })` and echo it as the `x-request-id` header. `proxy.ts` forwards it to pages.
- Never log secrets, passwords, cookies or full row contents; log ids, table names, counts and durations (`elapsedMs`).

## Internationalisation rules

- Every piece of text players see is translatable. Interface strings live in `src/content/seed/ui-strings.ts` (typed keys; English + hand-written de/ko/pl/ar); pages get them via `getDictionary(locale)` and pass the `Dictionary` object down as a prop to Client Components. Add a new key there with all five languages when you add UI text. Production reads them from the `ui_strings` table: a new key falls back to the bundled text automatically, but a **changed** key only reaches the site after `npm run db:seed -- --sync-ui` (or the Maintenance workflow's `sync-ui` task).
- Content fields are `Localized` JSON (`{ en, de, ... }`); read with `pick(value, locale)` which falls back to English. English is always the source language.
- Use logical CSS (`ms-`, `me-`, `ps-`, `pe-`, `start-`, `end-`, `text-start`) and `rtl:` variants, never left/right, so Arabic mirrors correctly. Put `dir="auto"` on elements that show content text (so English fallback reads correctly on RTL pages) and `dir="ltr"` on codes, numbers and clocks.
- Language list = `languages` table (seeded in `src/content/seed/languages.ts`); direction/font per code = `src/lib/i18n/languages.ts`. Adding a language means both places plus `npm run translate`. Latin, Korean and Arabic fonts are bundled; Japanese and Chinese use the device's fonts (`--font-japanese` / `--font-chinese` in globals.css) to keep the site light. UI strings for languages beyond the five hand-written ones come from the pipeline and are preserved by `--sync-ui` while the English text is unchanged.
- Translation is done only by the pipeline in `src/lib/translate`, triggered by Supabase webhooks → `POST /api/translate` or `npm run translate`. Never translate during a page render. Providers are behind `provider.ts` (`TRANSLATION_PROVIDER=anthropic|gemini|off`, auto-detected from the keys): `anthropic.ts` (Claude, default `claude-opus-5-5`, structured JSON output, `fallbacks: "default"`) and `gemini.ts` share the prompt, glossary, retry and JSON parsing; a new provider implements the same `translateFields` contract. Keep `off` working: the site must run with no provider at all. Rows carry a `source_hash` holding one hash per translatable column (JSON; older rows a single whole-row hash, honoured while it matches), so only the column whose English changed is sent to the model; keep that mechanism when adding tables (add them to `src/lib/translate/tables.ts` and `supabase/webhooks.sql`). Before writing a row back, the pipeline re-reads it and steps aside if the English changed meanwhile (a newer run owns it), merging only the languages it produced into the current value, so an admin's edit is never reverted by a slower run.

## Data and security

- Schema changes go in a new file `supabase/migrations/000N_<name>.sql` (don't edit `0001_init.sql` after it has been applied). Keep RLS on; the anon key may only read published rows. Writes use the service-role client (`src/lib/supabase/admin.ts`) from server code and scripts only — never import it in Client Components.
- Rich text is stored as HTML and must pass through `sanitizeRichText` on write and on render (`RichText` component).
- API routes that mutate or revalidate are protected by `TRANSLATE_WEBHOOK_SECRET` (`src/lib/api-auth.ts`). The public site stays login-free.
- **Admin area** (`src/app/[locale]/admin`, English only: it is the council's tool and the one exception to the i18n rule). Supabase Auth with Discord through `@supabase/ssr`. `src/lib/auth/server.ts` reads the session (`getCurrentUser`, cached per request; `checkAccess(role)` for actions) and must run behind Suspense or in an action/route; `proxy.ts` refreshes tokens for `/{locale}/admin` paths only and forwards `x-pathname`. **Next renders a page in parallel with its layouts, so a layout cannot keep page data out of the response**: `proxy.ts` sends signed-out visitors to the login page before anything renders, every admin page calls `requireEditor(locale)` before touching data, and the admin loaders return nothing without access (`checkAccess`); the `(gated)` layout only provides the chrome and the "no access" note. The login page sits outside the route group; `/auth/callback` finishes the OAuth flow. The header/footer entry (`AdminEntry`) is a client component: the chrome is static, so it reads the session state from the (non-HttpOnly) Supabase cookie in the browser (`src/lib/auth/session-hint.ts`, a hint only, never an access check), shows the key when signed out, the wrench "Admin panel" when signed in, and nothing on `/admin` paths, where the admin bar carries the identity and the single "Sign out". Roles live in `profiles.role` (`admin` > `moderator` > `member`, helpers in `src/lib/auth/roles.ts`); the owner is configured, not stored (`SITE_OWNER`: Discord handle, or an e-mail in development, optionally a comma-separated list locally; `src/lib/auth/owner.ts`): always admin, unchangeable, and alone appoints or removes admins (`roleChangeProblem`), admins appoint moderators. Pre-authorisations live in `role_grants` (matched on sign-in by Discord handle or e-mail); every write goes to `audit_log`. Admin reads are uncached service-role loaders (`src/lib/admin/*-data.ts`); writes are Server Actions (`src/lib/admin/*-actions.ts`) that parse `FormData` with the pure, unit-tested helpers in `forms.ts` / `kvk-forms.ts`, re-check the role, call `updateTag(CACHE_TAGS.kvk)` and `revalidatePath` of the editor. Write Localized columns through `localizedUpdate` (translations are kept only while the English is unchanged; the pipeline refills them). Child rows (`kvk_rules`, `kvk_coordinators`, `kvk_formations`) are never numbered by hand: inserts append (`nextSortOrder`) and the `MoveButtons` arrows call `moveRow`, which swaps neighbours and renumbers the list (pure `moveInList`). The language of the editor is a dropdown (`LanguagePicker`, `?lang=`), not pills, so it scales with the language list. Translated text is edited per language: English through the normal forms (`localizedUpdate` drops the other languages, the pipeline refills them), every other language through `saveTranslation` (`src/lib/admin/translation.ts`: writes one key with `withLanguage`, never touches `source_hash`, and refuses while `translationPending` so a running machine translation can't overwrite a manual fix). Profiles carry a self-declared `game_name` and `alliance_tag`, shown together as `[TAG] Name` (`formatGameName` in `src/lib/admin/profile.ts`, also the audit actor name; `parseProfileForm` splits a typed `[TAG]` prefix off the name); roles are still granted on the Discord handle. `ADMIN_DEV_LOGIN=1` plus `npm run dev:admin` give a password login in development builds only.
- **KvK battle plan** (`/kvk`): the `kvk_*` tables have no anon read policy — read them only through `createAdminClient()` in server code (`getActiveKvkPlan`). The visitor's cookie is an HMAC of plan id + password (`src/lib/kvk/access.ts`); verify it in a Server Component inside `<Suspense>` (`KvkGate`), strip `password` before passing the plan to any component, and keep the unlock check in the Server Action (`src/lib/kvk/actions.ts`). On any data problem return `null` (page shows "no plan"), never the seed plan. One `kvk_plans` row is active at a time; `event_type` says whether it is the internal castle battle or the cross-kingdom KvK (they alternate every two weeks). The intro may contain `{{when}}`, `{{date}}`, `{{time}}` and `{{utc}}` tokens (`src/lib/kvk/battle-tokens.ts`, pure and unit-tested): `BattlePlan` renders such an intro through the client `LiveIntro`, which fills them from `battle_at` in UTC until hydrated and in the visitor's zone and language afterwards (`Intl.RelativeTimeFormat`, no dictionary keys), so an intro never says "tomorrow" by hand. The translation prompt keeps `{{…}}` placeholders. `[KvK]` and `[TMP]` are the kingdom's two battle alliances (castle rallies / counter-rallies), not game terms. Attackers *rally*, defenders *garrison*: formation roles stay `rally_lead` / `rally_join` in the database for both sides, and `roleLabelKey(side, role)` (`src/lib/kvk/formations.ts`) picks the word shown (`kvk.role.rally_*`, `kvk.role.garrison_*`, or `kvk.role.lead|join` for "either side"); the admin form switches the words with the side dropdown.
- Schema changes: add `supabase/migrations/000N_<name>.sql`; the Deploy database workflow applies it on merge. Keep files idempotent (`if not exists`, `drop … if exists`) so a manual run and the CLI run can coexist.
- Seed data: `npm run db:seed` inserts missing rows only; `--overwrite` replaces seed rows (and drops their translations).
